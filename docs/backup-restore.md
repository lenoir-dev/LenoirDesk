# Pilot backup and restore

The external restore witness and encrypted backup stream are the current recovery boundary. Use the [recovery-witness procedure](recovery-witness.md) alongside this isolated restore drill; the unencrypted helper below is for synthetic testing only.

The supported exercise is PostgreSQL 18.6 on a single node. `scripts/mission07_restore_drill.py` creates two fresh isolated containers, migrates the source, seeds synthetic business work, makes a custom-format backup, simulates a post-backup external effect, restores the older copy, quarantines the ambiguous Slack action, requires an audited `confirm_unknown` decision and only then clears the outbound gate. It then runs the CRM current-state convergence integration test against that **restored database** with an isolated NATS container and synthetic HTTP providers. The temporary target database and broker ports bind only to random loopback ports. It deletes its synthetic dump, private test environment and containers. Run it with `python3 scripts/mission07_restore_drill.py` after building `relaydesk-migrate:latest`. The drill never targets the owner's `relaydesk-postgres-1` database and makes no real provider calls.

## Backup scope and consistency

`pg_dump -Fc` provides a consistent PostgreSQL snapshot of the RelayDesk database, including migrations, tenants, inbox/outbox, action/effect identities, encrypted credential ciphertext, audit rows, reconciliation checkpoints **and object ACLs**. It does **not** include PostgreSQL role definitions, Redis/NATS persistence, application binaries, provider account state, or the encryption master key. The target roles must be created by the versioned `deploy/postgres/01-roles.sh` before restore. The archive and restore deliberately preserve GRANTs; omitting ACLs was detected by the restored-database test because the webhook failed with HTTP 503. The migration image and restored database must be version-compatible; run the same committed migration set and inspect `goose_db_version` before any worker starts. This pilot procedure uses PostgreSQL 18.6 for both sides; cross-major restores are not validated.

For a private local backup, first choose an encrypted local volume and a directory excluded from Git. Stop no database writes for `pg_dump`; its snapshot is consistent. The privileged PostgreSQL role is needed because several forced-RLS tables cannot be completely dumped by `relaydesk_migrate`. Do not copy the resulting archive to tickets, CI artifacts or a source export.

```sh
python3 scripts/pilot_backup.py --source-container relaydesk-postgres-1 --output-dir tmp/private-backups
```

The script refuses a repository directory unless Git ignores it, creates the directory with `0700` and the custom-format file with `0600`, and validates its archive structure with `pg_restore -l`. The restore helper rejects group- or world-readable backup files. Neither helper encrypts the file itself. Keep it only on an approved encrypted volume or wrap it with an approved encryption tool whose key is managed separately. Limit backup retention and access under the owner's pilot policy; do not delete the only restorable copy without another verified backup. A structural archive check is weaker than a restore drill.

## Isolated restore and safety gate

1. Stop every worker that can reach the target. Record the backup timestamp, incident time, database version and source provider-account IDs. Prepare a fresh target container named `rd-restore-*`, on a private network with **no published database port**, the same PostgreSQL major version and roles created by `deploy/postgres/01-roles.sh`. Put temporary database passwords in a local ignored `0600` env file, not command arguments or shell history. Keep `RELAYDESK_OUTBOUND_EXECUTION_ENABLED=false` in every restored worker environment.
2. Run `python3 scripts/pilot_restore.py --target-container rd-restore-<id> --backup <private>.dump`. It refuses a nonempty database or a target outside the `rd-restore-*` naming boundary. It restores as `relaydesk_migrate`, then calls the versioned `enter_restore_recovery(...)` database function before any worker is started. If the restore or quarantine fails, do not start a worker.
3. Confirm `SELECT outbound_enabled,recovery_started_at,quarantined_notifications FROM restore_safety_gate WHERE singleton;` returns `false` and the uncertain count. The migration quarantines every nonterminal `slack_invoice_paid` action as `unknown` with `restore_uncertain`, supersedes its dispatch pointers, and marks linked runs unknown. The executor also checks this gate before claim and immediately before outbound HTTP. The independent worker process gate defaults to `false`; PostgreSQL's restored copy alone never grants process clearance.
4. Compare the backup boundary with provider-side evidence for effects that may have succeeded after it. For each quarantined Slack action, use the existing tenant-authorized, audited `confirm_unknown`, `leave_unknown` or acknowledged `risk_retry` decision. `confirm_unknown` requires exact channel and timestamp. `clear_restore_recovery(...)` rejects any still-unknown `restore_uncertain` notification. Do not use ad hoc SQL updates to bypass the decision log.
5. Recover the **same** encryption master key from the authorized separate secret store. Verify key version and a read-only Stripe/HubSpot/Slack account-identity check in the restored environment. A missing/wrong key must prevent provider work; never replace it with a random key to “unblock” ciphertext. Validate current Stripe state and HubSpot managed fields by bounded known-customer reconciliation, then inspect gaps in event discovery. A current-state projection cannot reconstruct every missing invoice fact.
6. After every uncertain notification is resolved and account bindings are checked, call `clear_restore_recovery('<incident-specific reviewed reason>')` as the restricted migration/maintenance role. Only then set `RELAYDESK_OUTBOUND_EXECUTION_ENABLED=true` in the new deployment's private environment and start a single worker. Verify the gate, run states, oldest outbox/due ages and provider error rates before retiring the old deployment. Rollback is to stop the new worker and retain the quarantined database for analysis; do not swap back to an older active worker against a divergent database.

The `pilot_restore.py` command intentionally leaves the target **in recovery**. Its SQL function is an explicit documented operation, not an implied automatic replay. `restore_safety_gate` in a backup may record `outbound_enabled=true`; therefore using `pg_restore` outside the guarded procedure and launching a worker with an already-enabled environment can still be unsafe. Production orchestration should add a non-database restore witness or equivalent immutable deployment gate before a release candidate. This pilot does not claim automatic detection of every out-of-band restore.

## RPO, RTO and limitations

The drill records `backup_seconds`, `restore_seconds`, `validation_seconds`, the observed backup-boundary-to-failure data-loss window, and failure-to-clearance recovery time. Compare these actual values to provisional RPO ≤15 minutes and RTO ≤60 minutes only for the measured dataset and machine. A tiny synthetic database cannot validate those objectives under production size, WAL volume, provider latency, key recovery time or human review. The synthetic Slack witness proves that a restored pending row can represent an already-accepted external effect; it does not claim a real Slack send. The drill's audited confirmation and post-restore CRM convergence exercise the existing decision and executor paths. Live provider recovery after an actual disaster remains a separate staging acceptance requirement.

Retention is independent of backups: raw webhook payloads are eligible for redaction after seven days, terminal sanitized attempts/runs after thirty days, and audit after ninety days. Event/effect identities are retained longer to prevent replay. Backups may retain data beyond in-database retention until their separate expiry. The pilot has no automated secure deletion, full tenant erasure or online encryption-key rotation; these require owner policy and production design.
