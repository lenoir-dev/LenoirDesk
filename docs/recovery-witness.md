# External restore witness and protected pilot backups

The outbound worker now needs three independent conditions: the deployment's explicit outbound setting, the SQL recovery gate, and an external witness file on a volume separate from PostgreSQL. Migration 38 records a random database incarnation and a monotonic effect sequence. Before each business action can reach a provider, the worker advances that sequence in PostgreSQL, durably writes the matching external file, and marks the action in flight in the file. It removes the mark only after an action outcome is durable. A new worker process refuses a missing/mismatched file or any in-flight mark. A normal clean restart with no in-flight action reuses the existing witness. Do not copy the witness volume into PostgreSQL backups.

For initial enrollment on a known current database, stop outbound workers, run all migrations, check provider account bindings and gate state, then set a non-secret incident reason in the shell and run `docker compose --profile maintenance run --rm witness enroll`. Enrollment requires a missing witness file, zero effect sequence and an open SQL gate; it writes an audit row. The Compose `witnessdata` volume is independent of `pgdata` and is `0700`/`0600` within the image. Never delete that volume to make a restored database start.

After any restore or witness mismatch, **keep every worker stopped**. Run `enter_restore_recovery(...)` with the maintenance role; this quarantines nonterminal Slack notifications. Review provider-side evidence, reconcile CRM current state and decide every `restore_uncertain` Slack action via the audited operator flow. With the SQL gate still closed, run `docker compose --profile maintenance run --rm witness rebind` using an incident-specific `RELAYDESK_RESTORE_WITNESS_REASON`. Rebind refuses unresolved restore-uncertain Slack work and records an audit row. Then call `clear_restore_recovery(...)`, start a fresh single worker and inspect backlog, unknowns, account bindings and metrics. The witness command is not a substitute for those reviews. The maintenance database URL stays in a one-off service, not the worker.

This protects against the common bypass of restoring an older SQL snapshot and starting the documented worker with an old `outbound_enabled=true` row. It also detects a backup taken while an external call was in flight: the external file retains an in-flight mark, even if the backup contains the same sequence. A crash between the database commit and file sync closes the gate conservatively. The witness is **not** a malicious-operator control: someone who copies or forges both the database and the external volume, runs an alternate binary, or restores a database while workers continue to make requests can defeat or race it. The pilot supports one active worker deployment sharing one witness volume; distributed fencing and high availability require a stronger external coordinator before production.

For encrypted pilot backups, use the official `age` CLI with a public recipient. Store its identity key outside the repository, backup directory, database and witness volume with `0600` permissions. `scripts/pilot_backup_encrypted.py` streams `pg_dump -Fc` directly to an `.age` file in a `0700` ignored directory; no plaintext dump is written. `scripts/pilot_restore_encrypted.py` authenticates the entire encrypted file with the separate identity before streaming it into a fresh isolated `rd-restore-*` target and entering SQL recovery quarantine. Missing/wrong keys fail before restore. A second decryption also must succeed; on any failure the isolated target remains unusable and workers stay stopped. Run a real isolated restore verification periodically; encrypted file presence alone is not recovery evidence. Keep backups for a proposed 7 daily and 4 weekly copies until the pilot owner selects a storage destination and schedule. Never upload local dumps or identity keys as CI artifacts. This workflow does not yet provide automatic off-host storage, retention enforcement or production KMS.
