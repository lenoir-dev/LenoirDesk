# LenoirDesk owner guide — local MVP

## Start and explore

Run `make up`, then open `http://localhost:58080/`. Sign in with the local Dex account shown in the README and create a workspace. The Overview checklist reports persisted progress. It does not create provider accounts for you.

Connections shows the provider account ID, test/simulation environment, credential health, last verification and required scopes. A workspace owner connects Stripe Test Mode with a restricted key that has **Accounts, Customers, Subscriptions and Invoices Read**. Missed-event discovery additionally requires **Events Read** for `GET /v1/events`; a connected credential must be checked before treating historical coverage as verified. Create a Stripe snapshot-event destination for the generated `/webhooks/stripe/{reference}` path and pin `2026-08-26.dahlia`. Supply that destination's webhook secret, never a Stripe CLI secret. Copy the path before submitting; LenoirDesk retains only its hash and never displays submitted secrets again. The owner begins HubSpot and Slack OAuth with the expected numeric portal/workspace ID. Install only in intended test accounts and confirm the verified identity on Connections. Named account evidence and credentials are intentionally excluded from this public source snapshot.

In Automation, choose the three verified connections, enter Stripe Test Mode Price IDs, choose the Contact policy and Slack channel ID, then review the behavior before activating a new immutable revision. The restricted Stripe key cannot enumerate Prices; obtain IDs from Stripe's test dashboard. Invite the Slack bot to a private channel before selecting it. `explicit_only` requires an operator link; `unique_upsert` may create a Contact using the managed unique key. Multiple matching subscriptions stop for review; activation does not backfill historical notifications. A paid invoice discovered first through reconciliation remains notification-suppressed even if its signed webhook arrives later; the [policy ADR](adr/0003-reconciliation-notification-policy.md) records the alternative awaiting product approval. Pause blocks new outbound effects but keeps accepted work durable. Only owner/operator may change the revision.

Runs is newest-first and limited to 25 rows per page; filters include retry waiting, blocked, needs attention, unknown and dead/DLQ. Run details show the source event, customer/invoice identity, revision, CRM and dependent Slack steps, attempts, safe provider-call references, confirmed Contact/message, next retry and operator decisions. A green succeeded run requires every required action to resolve.

For a Contact conflict, open **Review Contact mapping** from the affected run. Inspect a specific numeric Contact ID; the server reads its managed key and refuses an archived/missing Contact or conflicting key. A matching or unclaimed Contact can be explicitly bound with a reason. When the key is absent, check the identity outside RelayDesk before binding: email alone is insufficient. The bind is audited. Return to Run details and retry only the eligible CRM action. If a local mapping was lost, an archived Contact's unique key may permit a new active Contact; stop when identity cannot be established. For a Slack `unknown` action, inspect the exact channel: confirm an observed message with its timestamp, leave unresolved, or acknowledge duplicate risk before a retry. Ordinary Retry is deliberately unavailable. Viewer access is read-only. See the [recovery runbook](operator-recovery.md).

## Safe local demonstration

Run `make demo-local` for a dedicated synthetic Compose stack and browser walkthrough. It does not touch the ordinary development database or worker. The printed URL uses a local test OIDC identity and populated persisted workspace; the second URL controls only local provider simulators. Use `make demo-reset` for a fresh run, `make demo-down` to stop containers or `make demo-check` for an automatic contract check and cleanup. The full tour, exact isolation boundary and owner review steps are in the [LenoirDesk demo guide](lenoirdesk-demo-guide.md).

## Security and release boundary

Before enabling the local outbound worker, run migrations, verify provider account bindings and the SQL restore gate, then enroll the [external restore witness](recovery-witness.md) once on the current database with the maintenance service. Keep its volume separate from PostgreSQL backups. After any restore or witness mismatch, follow the audited quarantine/rebind procedure; do not delete the witness file to make the worker start. In the optional monitoring profile, `relaydesk_worker_outbound_enabled=0` makes an idle worker visible even when API readiness is healthy.

Keep `.env`, `.env.stage0.secrets`, OAuth tokens and provider keys outside Git and reports. Run `make publication-gate` before any future publication. For an explicit clean source export, `python3 scripts/safe_publish.py --export /absolute/path/outside/repo` writes only allowlisted files and a manifest, after scanning source/history and ignore rules. Use `--image <local-image>` to scan image layers. This command never publishes. Production rollout, provider account expansion and Git push require separate authorization and gates; core Stage 0 acceptance covers only the named test resources.
