# Owner guide: reconciliation and recovery

The **Reconciliation** screen in a workspace shows when Stripe history and known customers were last checked, any coverage gap, ages of queued work, and the oldest `unknown` or dead action. A green API readiness check alone does not mean that Stripe, HubSpot and Slack are synchronized. A viewer can inspect this status; an owner or operator can request a bounded historical scan.

To review a gap, open the workspace → **Reconciliation**. Check the affected Stripe connection, the last completed checkpoint, the unscanned window and the displayed gap code. If a connected key lacks Events Read, the screen reports a permission gap. A successful read-only Events API probe alone does not prove that the connected credential completed a historical scan. Do not claim a missing period was scanned until its checkpoint advances. Known-customer scanning can still compare current Stripe state with HubSpot, but cannot recreate every missing historical invoice fact.

For a permitted historical request, choose a verified Stripe Test Mode connection, a window within the last 29 days ending at least two minutes ago, a maximum of 1–500 events, and an audit reason. Review the preview page before submitting. The request advances in pages of at most 25, persists its cursor, and stops at the count cap or a provider gap. Recovered invoice history never sends Slack notifications. A recent invoice discovered before its signed webhook is also notification-suppressed; the later delivery does not promote it. This conservative pilot policy and its alternative are recorded in [ADR 0003](adr/0003-reconciliation-notification-policy.md). You can follow the request's persisted status on the same screen. A viewer cannot submit it, and one workspace cannot read another's checkpoints.

If an action is `unknown`, inspect the actual Slack destination before using **Runs → Recover**. Confirm an already-sent message only with the exact channel and timestamp; a retry of an unknown effect requires explicit duplicate-risk acknowledgment. After database restore, outbound work is disabled and nonterminal Slack notifications are quarantined until reviewed. The [restore procedure](backup-restore.md) explains the separate clearance gate; the [operations runbooks](runbooks/operations.md) cover common outages.

The pilot keeps minimal inbox and effect identities for deduplication, even after raw payload and old run details are removed. Retention and backup copies have separate privacy lifecycles. A request for full tenant erasure is an operational/legal policy decision, not a button in this interface.
